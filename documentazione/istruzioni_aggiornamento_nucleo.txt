LA REGOLA
 Ogni aggiornamento va PRIMA nella copia di prova:  /opt/lampp/htdocs/mydibest_pp   https://dibest2.unical.it/mydibest_pp
 Solo se li' va tutto bene, nel sito vero:          /opt/lampp/htdocs/mydibest      https://dibest2.unical.it/mydibest
 Si usa lo STESSO file .tgz tutte e due le volte. Se il tempo 1 va male, il sito vero non e' stato toccato.

COSA C'E' NEL PACCHETTO
 Tutto il codice del portale, con l'elenco di controllo SHA256SUMS_pacchetto.txt. NON ci sono: .env,
 uploads, cache, backups, il .htaccess della radice, i test, gli strumenti e la documentazione.
 Il .env, i file caricati e la cache non vengono mai toccati. I file che non esistono piu' nel codice
 nuovo restano sul server: il pacchetto aggiunge e sostituisce, non toglie.
 Cartelle nuove che il pacchetto porta: viste/ (con il suo .htaccess che la chiude al web), src/Http/,
 src/Portale/{Instradamento,Pagine}/, src/Anagrafi/Endpoint/, piu' nucleo.php nella radice.

TEMPO 2 - IL SITO VERO (solo se il tempo 1 e' andato bene in ogni sua parte)
 Imposta la data una volta (serve per i nomi delle copie di sicurezza):
      DATA=$(date +%Y%m%d_%H%M)
 A) Copia di sicurezza del DATABASE (il nome del database e' DB_NAME nel .env:
    per vederlo senza stampare la password:  grep '^DB_NAME' /opt/lampp/htdocs/mydibest/.env )
      sudo mysqldump --single-transaction --no-tablespaces NOME_DATABASE | gzip > ~/db_prima_aggiornamento_$DATA.sql.gz
      gzip -t ~/db_prima_aggiornamento_$DATA.sql.gz && ls -lh ~/db_prima_aggiornamento_$DATA.sql.gz
    (il file deve essere grande, non 0 byte)
 B) Copia di sicurezza dei FILE che stai per sostituire (l'avviso di tar sui file nuovi e' normale)
      cd /opt/lampp/htdocs/mydibest
      tar tzf ~/aggiornamento_completo.tgz | grep -v '^SHA256SUMS_pacchetto.txt$' > ~/elenco_file_$DATA.txt
      tar czf ~/backup_file_prima_$DATA.tgz --ignore-failed-read -T ~/elenco_file_$DATA.txt
      sudo cp /opt/lampp/htdocs/mydibest/.htaccess ~/htaccess_prod_prima_$DATA
 C) Estrai il pacchetto nel sito vero (l'elenco di controllo va nella tua cartella, non nel portale)
      tar xzf ~/aggiornamento_completo.tgz -C /opt/lampp/htdocs/mydibest --exclude=SHA256SUMS_pacchetto.txt
      tar xzf ~/aggiornamento_completo.tgz -C ~/ SHA256SUMS_pacchetto.txt
 C-bis) Il .htaccess, con il confronto PRIMA (vedi X1 in cima):
      diff ~/htaccess_nuovo /opt/lampp/htdocs/mydibest/.htaccess
      # se le differenze sono solo la regola 3b:
      sudo cp ~/htaccess_nuovo /opt/lampp/htdocs/mydibest/.htaccess
 D) Controlla che nessun file manchi o sia diverso (deve finire con TUTTO_OK)
      cd /opt/lampp/htdocs/mydibest && sha256sum -c --quiet ~/SHA256SUMS_pacchetto.txt && echo TUTTO_OK
 E) Controlla la sintassi con il PHP del server (non deve stampare righe di errore; alla fine FINE_CONTROLLO)

 F) Permessi: i file devono essere leggibili dal web

 G) Classi nuove (autoload): il portale le trova da solo con src/autoload.php se NON c'e' vendor.
    Questo aggiornamento porta molte classi nuove (src/Http/, src/Portale/Instradamento/...), quindi
    il controllo conta davvero (deve rispondere "niente vendor"):

SUBITO DOPO, PER GLI EVENTI DI DOMANI
 Gli eventi che prendono la presenza solo per statistica vanno sistemati a mano, una volta:
 pannello -> Eventi -> l'evento -> riquadro «Accesso e prenotazione» -> spegni «Rilascia l'attestato».
 Da fare PRIMA che il turno finisca: appena un turno e' concluso, cron_attestati.php manda gli attestati
 a tutti i presenti, e quello che e' partito non torna indietro.
 Se il turno di un evento cosi' e' gia' finito e l'attestato non e' ancora partito, spegnere
 l'interruttore basta: il cron salta quelle righe.
